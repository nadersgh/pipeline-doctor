# Design decisions and what I'd do differently

- **Heuristic reasoner as baseline and fallback.** I wrote a rule-based reasoner that works from evidence signals (schema drift, failing test type, SQL-changing commits) before adding LLMs. It gives the eval a free, deterministic baseline, and `FallbackReasoner` uses it for any step where the LLM call fails. The catch: it was tuned on the same catalogue, so its 100% says nothing about generalisation, and a missing API key used to quietly turn an LLM eval into a heuristic one. The eval now counts fallback steps and exits with an error when any step fell back.
- **Typed checks over free SQL.** The reasoner picks from 8 typed checks (`null_rate_by_load_day`, `orphan_keys`, `column_profile`, ...) whose SQL I wrote and tested, with `custom_sql` as the escape hatch. Typed checks are easy to review and keep cost down (about 1.6 queries per incident). They also limit what the agent can discover: a new failure mode needs custom SQL or a new check kind.
- **sqlglot guard as defence in depth.** DuckDB opens `read_only=True`, and Snowflake expects a SELECT-only role. `SqlGuard` still parses every query and rejects anything but one schema-qualified SELECT. The credentials are the real boundary; a parser-based allowlist will always have gaps, so I don't rely on it alone.
- **Snippet edits, validated before anyone sees them.** A fix is a list of exact `original` → `replacement` snippets that must match once, inside dbt folders, with no `..` or symlinks. Snippets avoid the line-number bookkeeping that makes model-written unified diffs fail to apply, and verifying one is a string match. They suit hotfixes, not refactors.
- **JEV is a rule gate, the LLM only vetoes.** The rules are deterministic, free, and name each failed check. The optional LLM judge can hold back a `proceed` but cannot overturn a rule failure, so a persuasive model cannot argue past a removed test. Rules only catch what I anticipated: with a real LLM the eval shows confident wrong diagnoses getting through (Haiku's proceed precision is 92%, and JEV sent all five of its confident wrong answers on to a human). The adversarial eval on the roadmap is the next step.
- **Hashing embedder for incident memory.** Signed feature hashing of unigrams and bigrams into 512 dimensions: no model download, deterministic in tests. It matches recurring failures that share table and error tokens and misses paraphrases. `TextEmbedder` is a protocol, so a real embedding model is a one-class swap once there is incident history to evaluate it on.
- **DuckDB for the demo, Snowflake not exercised live.** DuckDB lets the eval clone 53 workspaces and run them on a laptop in a couple of minutes. The Snowflake adapter (`QUERY_TAG`, statement timeout, `EXPLAIN` scan estimate) and sqlglot transpilation of fix SQL exist, but only the guard's Snowflake dialect is unit-tested. I would run the eval against a Snowflake account before claiming support.
- **Airflow 2.10, not 3.** The stack pins `apache/airflow:2.10.5`, and the log reader calls the `/api/v1` REST API, which Airflow 3 replaces with `/api/v2`. Porting the log reader and re-testing the callback is the main work.
- **FastAPI background tasks, not a queue.** The webhook stores the incident and runs the diagnosis in a `BackgroundTasks` job in the same process, and incidents are JSON files on disk. That is enough for one team and a demo. A restart drops in-flight diagnoses and two replicas would race on the files, so production needs a durable job queue and a database-backed repository.
